# EcoFin

**AI-платформа ресурсоэффективности для Казахстана.** Показывает, где объект
теряет ресурсы и сколько тенге можно вернуть.

Пользователь вводит текущее потребление электричества, воды и отходов.
Платформа сравнивает эти цифры со средними по региону для объектов такого же
типа, находит перерасход и с помощью Claude формирует конкретные меры — каждая
с оценкой экономии в натуральном выражении и в тенге по действующим тарифам.

Аудитории: домохозяйства, школы, малый бизнес.

## Проблема

Счёт за коммунальные услуги показывает сумму, но не отвечает на два вопроса:
много это или мало для такого объекта, и что конкретно сделать, чтобы платить
меньше. Энергоаудит стоит денег и доступен не всем, а универсальные советы
уровня «экономьте воду» не приводят к решениям.

## Решение

Три цифры из квитанции → сравнение с региональной нормой → конкретный план
действий с деньгами. Без датчиков, обследований и регистрации.

### Поток данных

1. **Онбординг** → `POST /api/profiles` → RPC `create_profile_with_baselines`
   создаёт профиль и его показатели **одной транзакцией**, `profile_id`
   сохраняется в localStorage.
2. **Кабинет** → серверный компонент читает профиль, показатели, бенчмарки и
   рекомендации напрямую из Supabase и считает отклонения от нормы.
3. **Генерация** → `POST /api/recommendations` → `generateRecommendations()`
   отдаёт Claude карточку объекта с посчитанными отклонениями → ответ
   валидируется → экономия переводится в тенге на нашей стороне → запись в
   `ai_recommendations`.
4. **Разметка** → `PATCH /api/recommendations` меняет статус на `applied` или
   `dismissed`, сумма экономии в шапке пересчитывается.

### Схема БД

Шесть таблиц: `profiles`, `regional_benchmarks`, `resource_baselines`,
`consumption_logs`, `ai_recommendations`, `org_units`. Плюс plpgsql-функция
`create_profile_with_baselines`. Всё в `supabase/schema.sql`, скрипт
идемпотентный.

## Как устроен AI-модуль

Ядро проекта — `lib/ai/recommendations.ts`. Ключевые решения:

- **Модель не считает деньги.** Она оценивает экономию только в натуральном
  выражении (кВт·ч, м³, кг). Перевод в тенге делает `lib/tariffs.ts`. Модель
  ошибается в арифметике и не знает тарифов, а цифра экономии — главный экран
  продукта.
- **Форма ответа задана схемой**, а не просьбой в промпте: `output_config.format`
  с JSON Schema делает markdown-обёртку и преамбулу невозможными на уровне API.
  Защитный парсинг при этом сохранён — снятие фенсов, `JSON.parse` в `try/catch`,
  поэлементная валидация; невалидный элемент отбрасывается, остальные выживают.
- **Отклонения считаются в коде**, а не моделью, и подаются ей готовыми — чтобы
  она не тратила внимание на арифметику и не ошибалась в ней.
- **Невозможные рекомендации отбрасываются.** Если заявленная экономия больше
  текущего потребления по ресурсу, элемент выкидывается: такая цифра
  подрывает доверие ко всему продукту.
- **Единицы измерения подставляются свои**, а не присланные моделью.
- **Сбой не роняет страницу.** Функция возвращает типизированную причину отказа
  (нет ключа, исчерпан баланс, таймаут, лимит запросов, ошибка API, пустой
  результат), а интерфейс показывает соответствующее сообщение с кнопкой
  повтора.

## Запуск локально

Нужны Node.js 20+, проект в Supabase и ключ Anthropic.

```bash
git clone <адрес репозитория>
cd ecofin
npm install
```

Накатить схему: открыть SQL Editor в Supabase, выполнить `supabase/schema.sql`
целиком. Скрипт создаёт таблицы, индексы, политики RLS и заполняет
региональные бенчмарки.

Создать `.env.local` по образцу `.env.example`:

```
NEXT_PUBLIC_SUPABASE_URL=https://<ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<publishable или anon ключ>
ANTHROPIC_API_KEY=<ключ с console.anthropic.com>
```

`NEXT_PUBLIC_*` — публичные ключи, доступ ограничивается политиками RLS.
`ANTHROPIC_API_KEY` используется только на сервере и никогда не должен
получать префикс `NEXT_PUBLIC_`.

```bash
npm run dev     # http://localhost:3000
npm run build   # проверка типов и сборка
npm run lint
```

## Что работает по-настоящему, а что на примерных данных

**Работает по-настоящему:**

- Создание профиля и показателей — реальная запись в PostgreSQL, одной
  транзакцией.
- Рекомендации — живой вызов Anthropic API на введённых пользователем данных.
  Заготовленных текстов в проекте нет.
- Расчёт экономии в тенге — детерминированный код на основе оценки модели в
  натуральном выражении.
- Сравнение с нормой, отклонения, панель организации, статусы рекомендаций —
  всё считается по фактическим данным профиля.

**Примерные данные, требующие замены перед боевым использованием:**

- **Тарифы** (`lib/tariffs.ts`): 25 тг/кВт·ч, 180 тг/м³, 12 тг/кг. Это порядок
  величины по Казахстану, а не выверенные значения конкретного поставщика.
  Для боевого использования нужны действующие тарифы поставщиков региона.
- **Региональные бенчмарки** (`supabase/schema.sql`): экспертные оценки на
  основе открытых данных Бюро национальной статистики РК по среднему
  потреблению домохозяйств и типовых нормативов для бюджетных учреждений.
  Собственные значения заведены для Западно-Казахстанской области, Астаны,
  Алматы и Шымкента; для остальных регионов используется общестрановой откат.
- **Аутентификации нет.** Профиль определяется по `uuid` в localStorage,
  политики RLS в демо-режиме открыты для роли `anon`. Перед продакшеном их
  нужно заменить на политики, привязанные к `auth.uid()`.

## Что планируется добавить

- Аутентификация и полноценные политики доступа вместо демо-режима.
- История показаний по месяцам (таблица `consumption_logs` уже в схеме) и
  динамика: показывать не только отклонение от нормы, но и собственный тренд.
- Подтверждение эффекта: сравнение потребления до и после применённой
  рекомендации вместо оценки модели.
- Реальные тарифы по регионам вместо констант и автоматическое обновление.
- Оценка стоимости внедрения и срока окупаемости для каждой меры.
- Импорт показаний из квитанции фотографией.
- Сравнение подразделений между организациями — бенчмарк «школа против школы».
